 You can let views access models from both containers by scoping each container to a different subtree and explicitly reading from the desired ModelContext when needed. SwiftData’s @Query always uses the nearest modelContainer in the environment; it can’t query two containers at once. But you can:

In MainSceneRoot line 25, how exactly does .modifier work?

************************************************************************************************************************

View.modifier(_:) applies a custom transformation to a view by wrapping it in a type that conforms to ViewModifier. It’s a general-purpose way to bundle and reuse a set of view changes. In your file, you’re using it to conditionally attach a SwiftData ModelContainer to the view hierarchy.

Here’s what’s happening at line 25:

• ContentView() produces a view.
• .modifier(PerWindowModelContainer(container: windowStore?.container)) applies your custom PerWindowModelContainer modifier to that view.
• The modifier’s body(content:) decides whether to call .modelContainer(container) (injecting the per-window SwiftData container) or just return the content unchanged.

So, at a high level:
• If windowStore?.container exists, the modifier returns content.modelContainer(container) — this means the environment for ContentView and its descendants will use the per-window container.
• If it’s nil, it just returns content as-is — the view keeps whatever model container is already in the environment (e.g., your global one from the app).

Breaking it down:

1. Your modifier type
 
 private struct PerWindowModelContainer: ViewModifier {
    let container: ModelContainer?
    func body(content: Content) -> some View {
        if let container {
            content.modelContainer(container)
        } else {
            content
        }
    }
}
 
• Content is the view the modifier is applied to (here, ContentView()).
• The modifier returns a new view that either wraps content with .modelContainer(container) or returns content unchanged.

2. Applying the modifier
    
ContentView()
    .modifier(PerWindowModelContainer(container: windowStore?.container))
    
• This is equivalent to:
   • If windowStore?.container != nil: ContentView().modelContainer(windowStore!.container)
   • Else: ContentView()

3. Why use a modifier here?
• You want to conditionally apply .modelContainer(...). SwiftUI modifiers like .modelContainer aren’t optional by themselves, so using a ViewModifier lets you encapsulate the “if container exists” logic cleanly.
• It keeps your body concise and avoids duplicating if let logic around the view tree.

4. Alternative syntax
You could write the logic inline without a custom modifier:

Group {
    ContentView()
}
.ifLet(windowStore?.container) { content, container in
    content.modelContainer(container)
}

But since there’s no built-in .ifLet for views, the custom ViewModifier is a neat, Swifty way to do it.

5. Important implication for SwiftData
Because .modelContainer sets the nearest container in the environment, placing this modifier on ContentView() means everything under ContentView will use the per-window container. If you have subviews (like SourceFilesView) that need to keep using the global container, you should move this modifier to only the editor subtree that needs the per-window container. Otherwise, @Query for global models will suddenly query the per-window store and show nothing.

In summary:
• .modifier applies your PerWindowModelContainer to ContentView().
• The modifier conditionally injects the per-window ModelContainer.
• This is a clean way to toggle environment configuration without duplicating view-building logic.

So, if MergedPDFDocument handles creation and deletion of model objects, and views can read them via @Query, how should a view go about updating the properties?

************************************************************************************************************************

Great question. With SwiftData, you have a few ergonomic options for updating model properties from views. Since your plan is:

• MergedPDFDocument handles creation/deletion for the per-window models (good).
• Views read per-window models using @Query (also good).

Then for updates, you can choose one or combine several of these patterns:

1) Bindable models in views (best for simple inline editing)

SwiftData @Model types are reference types; when a view holds one, you can mutate its properties directly and then save the context. For simple editing UIs, you can bind view controls to model properties:


import SwiftUI

  Notes:
• @Bindable gives you property wrappers ($section.title) to use with SwiftUI controls.
• You still call try? modelContext.save() to persist changes.

For lists:

2) Explicit actions that call into MergedPDFDocument

If you want to centralize business rules or re-render your merged PDF after updates, expose small helpers on MergedPDFDocument and call them from the view. For example:

In MergedPDFDocument:

func updateItem(_ item: PDFPageItemModel,
                name: String? = nil,
                trims: EdgeTrims? = nil,
                merge: MergeMode? = nil) {
    guard let ctx = windowModelContext else { return }
    if let name { item.name = name }
    if let trims {
        item.trimLeft = Double(trims.left)
        item.trimRight = Double(trims.right)
        item.trimTop = Double(trims.top)
        item.trimBottom = Double(trims.bottom)
    }
    if let merge { item.mergeModeRaw = merge.rawValue }
    do { try ctx.save() } catch { print("Save failed: \(error)") }
    refreshMergedDocument()
}

In a view:


struct ItemEditorRow: View {
    @Environment(MergedPDFDocument.self) private var doc
    @Bindable var item: PDFPageItemModel

    var body: some View {
        HStack {
            TextField("Name", text: $item.name)
            Button("Apply") {
                doc.updateItem(item, name: item.name)
            }
        }
    }
}

This gives you a single place to trigger downstream effects like refreshing the merged PDF.

3) Two-phase editing (local state, then commit)

For expensive updates (e.g., recalculating the merged PDF), it’s often better to let the user adjust values in local state, then commit:

struct TrimEditor: View {
    @Environment(\.modelContext) private var modelContext
    @Environment(MergedPDFDocument.self) private var doc
    @Bindable var item: PDFPageItemModel

    @State private var localTrims = EdgeTrims.zero

    var body: some View {
        VStack {
            // Controls bound to localTrims...
            Button("Commit") {
                doc.updateItem(item, trims: localTrims)
            }
        }
        .onAppear {
            localTrims = EdgeTrims(
                left: CGFloat(item.trimLeft),
                right: CGFloat(item.trimRight),
                top: CGFloat(item.trimTop),
                bottom: CGFloat(item.trimBottom)
            )
        }
    }
}

This avoids constantly saving and re-rendering while the user drags sliders.

4) Use transactions to coalesce updates

If you’re mutating several properties at once and want to avoid multiple renders and saves, you can batch them:

withAnimation {
    item.name = "New Name"
    item.mergeModeRaw = MergeMode.mergeRight.rawValue
}
try? modelContext.save()


You can also wrap these in a MergedPDFDocument helper to ensure a single refreshMergedDocument() call happens afterward.

5) Validation and business rules

If you have constraints (e.g., trims must stay within bounds), put those rules in MergedPDFDocument helper methods or custom setters in a wrapper type. Views should remain lightweight; business logic lives in your document/controller.

When to choose which

• Simple forms and inline edits: use @Bindable and call save() afterward.

Why the hang occurs only when switching directly from data → merge

Short version: you’re creating/destroying a complex AppKit hierarchy (two NSCollectionViews with compositional layouts and diffable data sources) at the same time you’re changing the container view structure (full-screen SourceFilesView → NavigationSplitView with multiple columns). In the data → merge transition, SwiftUI re-parents the SourceFilesView into a sidebar and simultaneously mounts DocumentEditingView (two NSCollectionViews). During this specific transition, the collection views’ layout invalidation + snapshot application are being repeatedly triggered by environment/size changes, which can create a feedback loop that never stabilizes (layout → invalidation → update → new snapshot → layout…). That’s why the beach ball appears and the debugger shows repeated collection view layout work.

A few concrete reasons this transition is uniquely fragile in your code:

• ContentView conditionally swaps the entire root structure:
   • In .data mode: a single HStack with just SourceFilesView filling the space.
   • In .merge mode: a NavigationSplitView with SourceFilesView moved into the sidebar, plus the middle and detail columns (including the NSCollectionViews).
   • When switching directly from data → merge, you’re both:
      • Relocating SourceFilesView to a different container (NavigationSplitView sidebar).
      • Instantiating DocumentEditingView (which mounts two NSCollectionViews).
      • Causing a large set of environment changes (column widths, geometry, toolbars, inspectors, etc.) all at once.

• DocumentEditingView.updateNSView unconditionally calls applySnapshotToBoth(animated:), which refreshes both diffable data sources every SwiftUI update. When the outer container is in flux (NavigationSplitView is computing column sizes and relaying geometry), this can trigger repeated snapshots while the layout is still reflowing.

• Your compositional layouts, decoration/backgrounds, and pinned headers/footers increase layout complexity. Combined with frequent invalidations (e.g., during column width transitions), they can cascade.

• If any binding or environment state used by the collection views (e.g., selected indices, sections array) is updated as a side effect of layout or snapshot, you can get a cycle: update → layout → state change → update again.

How to avoid it

You don’t need to rewrite your UI; you just want to make the data → merge transition less “noisy” and prevent snapshot churn during layout. Here are targeted strategies that work well together:

1) Stabilize the container transition with identity and phase

• Give the NavigationSplitView a stable identity so SwiftUI reuses it instead of tearing it down and rebuilding it. That reduces the amount of re-parenting:


if prax.praxPressMode == .data {
    SourceFilesView()
} else {
    NavigationSplitView(columnVisibility: $prax.columnVisibility) {
        SourceFilesView()
            .navigationSplitViewColumnWidth(min: proxy.size.width * 0.15, ideal: 300, max: proxy.size.width * 0.75)
    } content: {
        ContentDetailView()
            .navigationSplitViewColumnWidth(min: proxy.size.width * 0.25, ideal: 300, max: proxy.size.width * 0.75)
    } detail: {
        VStack {
            MergedDocumentToolbar()
            MergedDocumentView()
            MergedDocumentFooter()
        }
        .navigationSplitViewColumnWidth(min: proxy.size.width * 0.25, ideal: 300, max: proxy.size.width * 0.75)
    }
    .id("MainSplitView") // <- stable identity
}


• Optionally, introduce a small “phase” delay so you don’t mount DocumentEditingView on the same frame as the NavigationSplitView transition. Example: when switching to .merge, set a transient flag isMergeUIReady after a short DispatchQueue.main.async { } or a minimal debounce, and only then show DocumentEditingView. This avoids running expensive collection layout while the split view is still computing its initial sizes.

2) Make updateNSView idempotent and guarded

Right now, updateNSView always re-applies a snapshot:

func updateNSView(_ splitView: NSSplitView, context: Context) {
    print("updateNSView - context.coordinator.applySnapshotToBoth(animated: true)")
    context.coordinator.applySnapshotToBoth(animated: true)
}

Instead, only apply snapshots when the underlying data actually changes, or throttle updates:

• Track a “last applied” state (e.g., a hash of section IDs + item IDs + counts). If the new state matches the last applied, skip re-applying the snapshot.
• Alternatively, debounce snapshot application in the coordinator using a short timer so that multiple layout passes coalesce into one snapshot.

Pseudocode for guarding:

func applySnapshotToBoth(animated: Bool) {
    let newSignature = document.mergedPagesSignature() // e.g., combine ids/indexes
    guard newSignature != lastSignature else { return }
    lastSignature = newSignature

    var snapshot = NSDiffableDataSourceSnapshot<MergedPage, PageItem>()
    document.mergedPages.forEach {
        snapshot.appendSections([$0])
        snapshot.appendItems($0.pageItems)
    }
    leftDataSource?.apply(snapshot, animatingDifferences: animated)
    rightDataSource?.apply(snapshot, animatingDifferences: animated)
}

And in updateNSView, don’t force it every time; let the coordinator listen for actual model changes (e.g., via a callback or by observing the MergedPDFDocument’s published state) and call applySnapshotToBoth when necessary.

3) Avoid layout invalidation loops from pinned headers/footers during transition

Pinned headers/footers and decoration backgrounds are fine once the layout has stabilized, but during the split view’s initial sizing they can cause repeated invalidations. Two pragmatic mitigations:

• Disable pinning during the first mount, enable after the initial layout settles (e.g., after the first viewDidLayout or with a small async dispatch).
• Or keep pinning but avoid re-applying the snapshot while the split view is still adjusting column widths (use the debounce/guard above).

4) Ensure selection mirroring doesn’t feed back into snapshot churn

Your coordinator mirrors selection between the left/right collection views. If any selection change triggers a SwiftUI state change that causes another snapshot, you can get a loop. Make sure:

• Selection mirroring only updates the other view’s selection without causing new snapshots (i.e., don’t call applySnapshotToBoth because of selection changes).
• If prax.selectedPageItems is @Observable/@Bindable and triggers view updates that in turn call updateNSView, the guard in (2) will prevent pointless snapshot churn.

5) Keep the per-window ModelContext stable across the transition

You already scoped global vs per-window contexts. When moving from data → merge, confirm that the per-window context used by DocumentEditingView remains the same instance. If the environment injects a new container/context instance right as the split view appears, your coordinator may rebuild data sources and layouts at the same time it’s applying snapshots. Keep the per-window .modelContainer scoping stable for the editor subtree, and avoid swapping it at the same moment the split view is mounted.

6) Don’t rebuild compositional layouts and registrations every update

You’re correctly doing that work in makeNSView and configure(...) once. Verify that you’re not inadvertently re-registering or rebuilding layouts due to view identity changes. The .id("MainSplitView") helps keep the split view stable, so the inner views don’t get torn down and re-built.

A minimal, high-impact checklist

• Give the NavigationSplitView a stable identity with .id("MainSplitView").
• Guard applySnapshotToBoth so it only runs when sections/items actually changed (or debounce it).
• Optionally defer mounting DocumentEditingView by one runloop tick after switching to .merge.
• Keep the per-window model container/context instance stable for the editor subtree during the transition.
• Ensure selection mirroring doesn’t trigger snapshots.

These changes don’t alter your architecture; they just remove the conditions that cause layout to be invalidated repeatedly at the exact moment the split view is resizing and the NSCollectionViews are mounting.
